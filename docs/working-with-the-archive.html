How this works
Capture and question are two halves. Hooks write each session to InventDB as it runs. The InventDB MCP server is registered with your Claude Code, so I can query that same archive mid-conversation — in plain language from you, as SQL underneath. You never write the query. I read the result and answer from it.

2. How I use the archive while building for you

You don't have to ask. When I'm working on something, the archive is a place I check — the same way I'd read the code before changing it.

Before I start: has this already been solved here?

If you ask me to add a benchmark harness, the first useful thing I can do is not write one. I search the archive, find the 4 August TPC-C session, and start from its conclusions. The alternative is confidently rebuilding something your team already owns.

While I work: what has already been ruled out?

If I'm chasing a write-path slowdown, the 19 August investigation tells me the bloom filter was traced and the probe was cleared. That is a dead end I get to skip. Failed attempts are the most valuable thing in the archive precisely because nothing else keeps them — every other artifact in your toolchain is a record of what worked, written by the winner.

When I write throwaway tooling: what did we learn last time?

Someone wrote a watcher script mid-run on 16 August and left the lesson in a comment:

16 Aug 2026 · a watcher script written mid-run # Wait for the battery legs, then run the c/s TPC-C legs. Matches
# failure markers too - a watcher that greps only the success line
# is silent through a crash and costs hours.

That lesson exists nowhere in the codebase. It cost someone hours to learn. Because the session was kept, the next watcher I write for you starts with it already applied.

Before I tell you it's done: how did we verify this last time?

The archive holds 2,674 pre-edit file snapshots and 7,889 edits with exact before-and-after text. Alongside them sits the command output that was taken as proof — including the times that proof was a stale binary or the wrong build. Reading how verification actually went is how I avoid repeating a false green.

Why this is different from me reading your repository
Your repository tells me what the code is. The archive tells me what your team tried — the constraint discovered at hour three, the approach abandoned, the benchmark that overturned the plan. Both matter, and only one of them is normally written down.

The archive survives what people don't

Session capture ran for a month on one piece of work — “Store Claude sessions in InventDB via hooks”, 29 July to 29 August, 12,679 API requests. Along the way the context was compacted twice on 28 August, and resumed by hand once.

Compaction throws away detail the model no longer has room for. In that session it threw away the bloom-filter investigation. The archive kept it — which is the only reason I can quote it to you now, and the reason a month-long thread can be handed to another person, or another machine, without starting over.

The honest limitation
This is a record of what was attempted, not a record of truth. A session can contain a wrong conclusion stated confidently — the 19 August entry is literally someone correcting themselves. When I answer from the archive I'll tell you the date, the session, and the wording, so you can weigh it. Treat it as evidence, not as documentation.
Getting there. Install the plugin, point it at your InventDB instance, and let it build forward — /plugin marketplace add inventdb/inventdb-claude-code-sessions, then /inventdb-sessions setup <url>.
