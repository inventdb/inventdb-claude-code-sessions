Ten things a session archive is for

What developers, teams and engineering organisations actually get from mirroring Claude Code sessions into InventDB — each one demonstrated with a query and a measured result.

docs/ten-uses.html · August 2026 · plugin v0.1.0

The premise

A session log is not a chat transcript. It is an execution record: every command with its output, every file’s pre-edit state, every approach that was tried and abandoned, and the token cost of all of it. It is the only engineering artifact that contains the work which failed — everything else in the toolchain is a record of success, written by the winner. Claude Code removes it on a retention timer, 30 days by default. The ten uses below are what you get for keeping it instead.

The number that makes the case

Those rows arrived from 694 transcript files. Only 282 of them still exist on disk — the retention timer has already deleted the other 412. For roughly three fifths of this archive, the mirror is the only surviving copy. That is not a projection about what could be lost; it is what was already lost on one machine in three months.

How these numbers were measured

Figures are a snapshot as of 23 August 2026. The archive is written to continuously by live capture, so totals move between queries — treat them as a reading, not a constant.

Each figure was taken with COUNT(*) or SUM under an explicit predicate, run twice and discarded unless both runs agreed, then cross-checked two further ways: against the shipper’s own byte-and-line watermarks (694 files, 404,064 lines shipped), and against a direct scan of the surviving local transcripts. Two counts reconcile exactly across all three methods — pr-link at 877 rows and file-history-delta at 1,176.

Identifiers are redacted throughout. Branch names, directory paths, file names, symbols and session titles are replaced with roles or with placeholders such as <error text> and <filename>. The shape of every query is real; only the nouns are removed.

1 AI spend attribution

“What is our agent spend, and which piece of work incurred it?”

Every assistant line carries its own usage block, stored as a nested document rather than a string — so token accounting is a SUM, not a parsing exercise.

SELECT SUM(message.usage.input_tokens)               AS input_tokens,
       SUM(message.usage.output_tokens)              AS output_tokens,
       SUM(message.usage.cache_read_input_tokens)    AS cache_read,
       SUM(message.usage.cache_creation_input_tokens) AS cache_write
FROM <ns>.session_line;
MeasureTokens, 94 days
Uncached input15,151,918
Output294,180,047
Cache read103,705,719,561
Cache write1,265,627,648

Cache reads are 103.7 billion tokens — roughly 6,800× the uncached input, and 82× the cache writes that created them. No vendor dashboard surfaces that ratio, and it is the single largest lever on the bill. Multiply each column by your rate card and the query is a finance report.

The same ratio computed independently from the local transcripts, over the 58% of the corpus that still exists on disk, comes out at 8,212× and 78× — same order, from a different source, which is what makes it worth quoting.

The same aggregate splits by branch, which turns an unallocatable line item into per-feature cost accounting:

SELECT git_branch, COUNT(*) AS lines,
       SUM(message.usage.cache_read_input_tokens) AS cache_read
FROM <ns>.session_line
WHERE git_branch IS NOT NULL
GROUP BY git_branch ORDER BY cache_read DESC;

2 Cross-team recall

“Has anyone already hit this? What did we try that failed?”

The archive keeps the dead ends, not just the commit that survived. Without it, the second developer to hit an error pays the full cost of the first one’s investigation.

SELECT session_id, ts, git_branch, cwd
FROM <ns>.session_line
WHERE message.content LIKE '%<error text>%';

In this archive, a search for one compiler error class returns 241 rows — every occurrence, with the diagnosis and the fix that followed it in the same session. A search for a single internal function name returns hits in three distinct sessions with an order-of-magnitude spread between them, which immediately separates the session that did the real work from the two that brushed past it.

Two query rules worth knowing

  • Search message.content, not raw. Each line is stored as a nested document, so its structure is queryable. raw is populated only for lines that failed to parse — searching it will silently return nothing.
  • Do not add ORDER BY to a query whose only filter is a single LIKE. Sort client-side, or add a second predicate. ORDER BY is safe alongside equality filters, IS NOT NULL, GROUP BY, or two or more LIKE terms.

3 Incident forensics

“This broke last Tuesday. What actually changed, and what convinced us it worked?”

Claude Code snapshots a file’s state before it edits it, and those snapshots are mirrored with everything else. In this archive:

Line kindRowsWhat it gives you
file-history-snapshot4,766Full pre-edit file state
file-history-delta1,176Incremental change records

That means a file’s prior contents are recoverable even when the change was never committed, was squashed away, or was reverted before anyone looked at it. The edits themselves are equally reachable — a two-predicate search for edits touching one source file returns 72 lines, each holding the exact before and after text:

SELECT ts, session_id, message
FROM <ns>.session_line
WHERE message.content LIKE '%<filename>%'
  AND message.content LIKE '%old_string%'
ORDER BY ts;

And critically, the command output that was taken as proof is stored beside the change. A green test run that was actually a stale binary, a benchmark that measured the wrong build — the archive shows what was believed, not just what was done.

5 Audit trail for AI-authored code

“Which model wrote this, under whose instruction, on what date?”

Every row carries its own provenance: model, git_branch, cwd, cc_version, ts, last_prompt, and the permission mode in force. Five distinct models appear across this 94-day window, so “which model produced this change” is a real question with a real answer — for every one of the 407,063 rows.

SELECT ts, model, git_branch, cc_version, last_prompt
FROM <ns>.session_line
WHERE session_id = '<id>' AND kind = 'assistant'
ORDER BY seq;
For regulated organisations this is not a report — it is the precondition. Where AI-assisted changes must be attributable and reviewable after the fact, an unrecorded agent session is the blocker that keeps adoption at pilot scale. A queryable, tamper-evident archive is what turns the answer to “can we use this in production” from no into yes.

6 Onboarding and expertise routing

“How does this subsystem really work, and who do I ask?”

A new joiner reading the final code sees the answer without the reasoning. The archive holds the reasoning: the constraints discovered the hard way, the approach abandoned in hour three, the measurement that overturned the plan.

SELECT session_id, COUNT(*) AS hits
FROM <ns>.session_line
WHERE message.content LIKE '%<symbol>%'
GROUP BY session_id ORDER BY hits DESC;

Because sessions carry Claude Code’s derived title, the index reads as a work log rather than a wall of UUIDs — for example, this plugin’s own build sits in the archive as “store claude sessions in inventdb via hooks”, 20,898 rows. Take the highest seq per session, since titles are refined as a session develops:

SELECT session_id, title, MAX(seq) AS lines
FROM <ns>.session_line
WHERE title IS NOT NULL
GROUP BY session_id, title ORDER BY lines DESC;

7 Tool and command inventory

“What are our agents actually doing all day?”

Because PostToolUse is captured with no matcher, every tool invocation lands in the archive. Counting them across this window:

Shell execution outnumbers file modification — Edit and Write combined — by 3.6 to one, and outnumbers reading by more than three to one. That has direct consequences for how you write a permission allowlist, and it is not what most teams guess when asked. The same data supports reviewing which commands agents run unattended, and spotting risky patterns before they become policy questions.

8 Session revival and handoff

“Pick up where a colleague stopped — on a different machine, a week later.”

SELECT seq, kind, role, message
FROM <ns>.session_line
WHERE session_id = '<id>' ORDER BY seq;

The largest session in this archive is 168,686 rows, with two more at 82,399 and 77,803 — far beyond what any context window holds, which means the archive is the only complete copy in existence. Compaction is visible too: session_event rows record SessionStart with source: "compact", so the detail that left the live context on compaction is still queryable in the mirror afterwards.

Local transcripts are per-machine and subject to a retention timer. The archive is neither, so a session survives a laptop rebuild, a departure, or a timezone.

9 Harness quality engineering

“Did that change to our agent configuration actually help?”

The archive is a measurement substrate for your own setup. session_event distinguishes clean completions from abnormal ends via reason; queue-operation rows (27,217) expose interruptions and re-steering; mode rows (18,808) show permission-mode switches.

Together these let you A/B a project-instruction change, a model swap, or a tool-permission policy and measure the result — retry rates, interruption rates, tokens per completed task — instead of arguing about it. Every organisation running agents at scale is currently tuning this configuration blind.

10 Mining sessions into durable artifacts

“Turn what we learned into something that outlives the session.”

The archive is a corpus. It generates runbooks and decision records from how work was really done, harvests recurring corrections into project instructions, and yields evaluation sets built from genuine failures rather than synthetic ones.

Attachments come along for the ride: 863 rows carry 907 inline binaries — screenshots, diagnostics, generated images — uploaded as real InventDB attachments on the row that produced them, so the evidence stays joined to its context. pr-link rows (877) tie sessions to the pull requests they shipped.

SELECT session_id, seq, attachments
FROM <ns>.session_line
WHERE attachments > 0 AND chunk_idx = 0;
Ranked last only because it is derived value. It needs the other nine to have filled the archive first — but it is the one that compounds.

Reproducing these on your own archive

Install the plugin, point it at an InventDB instance, and let it build forward — or backfill your history in one command.

/plugin marketplace add inventdb/inventdb-claude-code-sessions
/inventdb-sessions setup https://your-instance.inventdb.com

Then query with the sql tool over MCP, or POST /sql directly. Every query on this page runs unmodified against a fresh archive — substitute your namespace for <ns>.

Two things that make the difference

  • Nested document storage. Each transcript line is stored with its structure intact, so message.usage.input_tokens, message.model and message.content are real queryable fields. If lines were kept as opaque strings, only uses 2 and 3 would work at all — and the cost accounting in use 1 would be impossible.
  • Schemaless writes. Namespaces and types are created on first write, so nothing is declared in advance and no migration is needed when the transcript format gains a field.

Summary. A team’s session logs are the only record that includes the work that failed. Everything else in the toolchain is a record of success, written by the winner. That is what makes the archive worth keeping — and why a 30-day default deletion is the wrong place for it.
